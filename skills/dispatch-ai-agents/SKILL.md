# Dispatch AI Agents

## 环境信息

- **cc**：`<CC_PATH>`，模型固定 `opus[1m]`（Kimi），token 量大
- **codex**：`/opt/homebrew/bin/codex`，需 TUN（Clash 7890），默认 `gpt-5.4`（当前观察值，可能随版本变化）

---

## /army 协作流程

用户通过 `/army` 触发时，按以下流程执行，不可跳过任何步骤。

### 第一步：判断

评估任务的三个维度，用一两句话展示给用户：

1. **规模**：需要读/改 ≥3 个文件，或单文件 ≥200 行，或产出 ≥100 行？
2. **推理**：需要深度推理、架构决策、review？
3. **联网**：需要搜索外部信息？

### 第二步：输出计划

必须输出以下计划表：

**目标**：一句话说明要达成什么

| 步骤 | 谁做 | 做什么 | 产物 |
|---|---|---|---|

「谁做」取值：我 / cc / codex / 用户

**自检（出计划前必须过一遍）**：
- 如果计划里「我」做的步骤 ≥5 个 → 审视哪些可以合并派给 cc 批量做
- 如果「我」连续做 ≥3 个同类操作（改文件/review/搜集上下文）→ 必须改为派 cc
- 如果全是「我」做 → 必须解释为什么不需要外派，否则强制至少派一个步骤给 cc 或 codex

附一段「为什么这样分工」：每个角色分到活的理由（一句话）。

### 第三步：等待确认

输出计划后**立即停下来**，等用户回复。
禁止在同一条消息里既输出计划又开始执行。
用户确认后才进入执行。

### 第四步：执行

- 按计划表逐步执行
- **可并行的步骤应并行执行**：如果多个步骤之间没有依赖关系（如分别 review 不同文件、分别搜集不同模块上下文），同时启动，不要串行等待
- 需要调用 cc 时，读本目录下 `cc-reference.md`
- 需要调用 codex 时，读本目录下 `codex-reference.md`
- 多方协作时，读本目录下 `collaboration.md` 了解文件规范和交接模板
- **所有工具产出必须写到文件**，调度者只读文件摘要，不消费 stdout 大段输出
- 每步执行后验收产物（文件存在且非空），异常时重试或降级
- 每完成一个步骤，简短汇报进度
- 全部完成后，向用户汇报最终结果

## 任务路由：四维决策矩阵

按 **推理强度 × 执行规模 × 失败代价 × 可验证性** 决定派给谁：

| 推理强度 | 执行规模 | 失败代价 | 派给 |
|---|---|---|---|
| 低 | 大（文件多/并行） | 低 | **cc** |
| 低 | 小（≤2 文件，≤50 行改动） | 低 | **Cursor 自己做** |
| 高 | 任意 | 任意 | **codex**（TUN 可用时） |
| 低 | 任意 | **高**（迁移/生产/删除） | codex 先出方案，cc 按检查点执行 |
| 高不确定 | 小 | 低，可快速验证 | cc 探路 → codex 审核方案 |

**速查——以下场景直接派 cc，不要自己做**：
- 改 ≥3 个文件的同类内容（统一格式、批量重命名、模板替换）
- 写/改文档且产出 ≥100 行
- 搜集 ≥3 个模块的上下文
- review ≥2 个文件

**速查——以下场景派 codex**：
- 架构决策、方案对比
- 审查高风险改动（删除/迁移/权限变更）
- 根因分析、边界条件识别

## 推荐编排模式

| 模式 | 适用场景 | 流程 |
|---|---|---|
| **A** | 批量执行 | Cursor 决策 → cc 批量执行 → Cursor 验收 |
| **B** | 复杂改动 | cc 探路读上下文 → Codex 定方案 → cc 落地 → Codex review |
| **C** | 小改 + 把关 | Cursor 小改 → Codex review |
| **D** | 高风险操作 | Codex 出方案和检查点 → cc 按检查点逐步执行 → Codex 验收 |

---

## 降级策略

```
codex 不可用（网络/CLI/登录任一失败）→ cc --effort high 或 Cursor 自己做
codex 配额紧 → 优先 gpt-5.4-mini，能用 cc 的不用 codex
Cursor quota 紧 → 重活全派 cc，Cursor 只调度汇报
两者都挂 → Cursor 独立完成，告知用户
```
