# Codex 视角建议：三工具调度体系审视

基于对 `README.md`、`rules/ai-dispatch.mdc`、`cursor-settings-rules.txt`、`skills/dispatch-ai-agents/SKILL.md`、`skills/check-ai-usage/SKILL.md` 的阅读，这套体系已经有清晰的意图和基本分工，但从 Codex 这类偏深度推理/review 工具的视角看，当前更像“经验规则集合”，还没有完全升级成“稳定可复用的调度协议”。

我会先给结论：这套体系的方向是对的，尤其是把 Cursor 固定为用户交互与验收节点、把 cc 作为体力执行层、把 codex 保留给高价值推理任务，这个定位合理。但现在的主要风险在于职责边界还不够硬、交接物不够标准、验证闭环不够强，导致一旦任务稍复杂，就容易退化成“换一个模型继续试”，而不是“按预定义流程稳定执行”。

## 一、当前最值得优先修的点

### 1. 文档之间已有规则冲突，系统会被自己稀释

最明显的是输出路径规范不一致：

- `README.md:88-109` 和 `cursor-settings-rules.txt:14,20` 仍然示例写 `/tmp/...`
- `skills/dispatch-ai-agents/SKILL.md:47-49` 又明确要求必须写到 `_agent_work/`

这不是小问题。因为调度系统的可执行性依赖“示例即规范”，一旦主文档、Rule、Skill 给出不同约束，Agent 往往会选自己最熟悉或最短的那条路径，结果就是：

- 产物位置不可预测
- 用户难以追溯
- 后续 resume / review / diff 对不上

建议：

- 统一把 `/tmp/` 从 README 和 Cursor settings 中移除
- 明确 `_agent_work/` 是唯一默认协作目录
- 再细分子目录，例如：
  - `_agent_work/context/`
  - `_agent_work/plans/`
  - `_agent_work/reviews/`
  - `_agent_work/logs/`

### 2. 任务路由原则仍然偏粗，容易把“深度推理”和“高风险执行”混为一类

当前规则基本按“量大给 cc，难题给 codex，小改自己做”来分，这对于简单任务足够，但复杂任务不够精确。

真正影响调度的维度至少有 4 个：

- 推理强度：是否需要根因分析、架构权衡、review 判断
- 执行规模：文件数、命令数、并行度、上下文长度
- 失败代价：改坏后是否难回滚，是否涉及迁移、生产配置、数据操作
- 可验证性：是否能靠测试、lint、diff 明确判断对错

例如：

- “改 30 个文件的机械重构”不一定需要 codex，需要的是 cc 批量执行
- “只改 1 个文件，但要判断竞态根因”则非常适合 codex
- “改数据库迁移脚本”文件不多，但失败代价高，也不该简单视作执行类任务

建议把调度矩阵从“按任务类型”升级为“按风险和验证方式”：

- 高推理 + 高失败代价：codex 先做方案/review，执行可交给 cc 或 Cursor
- 低推理 + 高执行量：cc
- 低推理 + 低执行量：Cursor 自己做
- 高不确定性但可快速验证：可以先用 cc 探路，再让 codex 审核方案

### 3. 缺少标准化交接协议，导致多工具协作不可控

现在的“交接”主要依赖自然语言提示，比如“分析结构，结果写到某个文件”。这在轻任务上够用，但一旦涉及串行协作，缺少固定字段会让后续工具难以可靠消费前一个工具的产物。

建议定义最小交接模板，至少包含：

- `task`
- `scope`
- `constraints`
- `assumptions`
- `proposed_changes`
- `open_questions`
- `verification`
- `handoff_to`

可以用 Markdown，也可以要求 JSON front matter + Markdown 正文。重点不是格式本身，而是下一棒工具必须知道：

- 上一棒到底做了什么
- 哪些是事实，哪些是猜测
- 哪些点已经验证，哪些还没验证

如果没有这个层，三工具协作很容易变成三个 Agent 各自重建上下文，浪费 quota，也放大误判。

## 二、主要风险

### 4. `--dangerously-skip-permissions` 被写成默认姿势，安全边界太松

在 `cursor-settings-rules.txt:12` 和 `skills/dispatch-ai-agents/SKILL.md:56-57,89-95,111-112` 中，cc 基本命令和示例都默认带 `--dangerously-skip-permissions`。

这对“追求低摩擦调度”是方便的，但从 review 视角看，这相当于把执行层的安全阀常态化关闭了。风险包括：

- 超范围读写
- 错删文件
- 在含敏感信息目录中误操作
- 用户本来只想“分析”，结果工具直接开始改

建议至少分成三级：

- 只读任务：禁止危险跳过权限
- 工作区写任务：仅允许 workspace-write
- 高风险任务：需要用户明确确认，或至少要求先生成计划/补丁再执行

也就是说，不要把“方便”写成“默认”，要把“越权”写成“升级路径”。

### 5. TUN 检测只检查网络，不检查 Codex 实际可用性

当前 TUN 检测是：

```bash
curl -s --max-time 3 https://api.openai.com > /dev/null 2>&1 && echo "tun_ok" || echo "no_tun"
```

这只能说明“到 OpenAI 域名的网络可能通”，不能说明：

- Codex CLI 已安装且可执行
- 当前账号已登录
- 模型可用
- 命令参数未漂移
- review 子命令可用

建议把“codex 可用”拆成两层：

- 网络可达性检查
- CLI 健康检查

例如定义一个轻量 smoke test，验证：

- `codex --help` 或版本命令成功
- 一个最小 `exec` 可返回
- 失败时把原因分类为：网络、认证、CLI 版本、模型不可用

否则现在的降级判断会误把“CLI 坏了”当成“TUN 不通”。

### 6. 模型名和 CLI 参数被硬编码，未来容易漂移失效

文档里直接写死了：

- `gpt-5.4`
- `gpt-5.4-mini`
- `gpt-5.3-codex-spark`
- `-c model_reasoning_effort=high`

这适合作为当前经验，但不适合作为长期规则。模型名、默认模型、参数名、review 子命令行为都可能变化。

建议：

- 在 Skill 里把“当前推荐值”和“可替代探测命令”分开写
- 为 codex 增加一个“能力探测”步骤，而不是假定命令永远成立
- 把“默认模型”表述成“当前观察值”，不要写成强约束事实

### 7. 没有并发写入治理，多实例 cc 容易互踩

体系鼓励 cc 并行多实例，这本身没问题，但规则没有定义：

- 谁拥有哪些文件
- 哪些路径允许并行写
- 同一文件是否允许两个 Agent 同时改
- 汇总时以谁为准

如果并行只是“多开两个进程”，但没有文件 ownership 约束，越大的任务越容易发生：

- patch 冲突
- 后写覆盖前写
- 一个实例基于旧上下文推翻另一个实例结果

建议增加并发协议：

- 并行任务默认只允许读共享上下文
- 写入必须按文件/目录分区
- 共享文件改动只能由一个“集成者”负责
- 并行结果先写建议稿，再由单线程工具统一落盘

### 8. 缺少验证闭环，当前更像“派发体系”而不是“交付体系”

目前规则强调了谁做什么，但没有把“做完以后如何证明做对”写成强制流程。

一个稳定的闭环至少应该是：

1. 路由
2. 执行
3. 验证
4. review
5. 向用户汇报变更与风险

当前只有 `codex review --uncommitted` 这类建议命令，但没有定义哪些任务必须跑：

- 测试
- lint
- typecheck
- build
- diff 审查
- 回归点清单

建议把验证策略内建到 dispatch 协议中：

- 机械改动：至少 diff + lint
- 逻辑改动：至少针对性测试 + diff
- 架构改动：方案审阅 + 关键路径验证
- 无法验证时：必须在交接文件里明确写 `unverified`

## 三、遗漏项

### 9. 缺少“任务分级”，无法表达高风险操作的特殊流程

这套规则默认所有任务都可以按同一套调度思路处理，但实际上应至少区分：

- L1：只读分析
- L2：普通代码编辑
- L3：批量重构
- L4：脚本执行/依赖安装/生成文件
- L5：数据库、部署、密钥、删除性操作

L4/L5 的执行方式、审批需求、回滚要求都不该和普通改代码相同。

### 10. 缺少“事实/推断”分层，review 结果容易被误当事实

Codex 在复杂 bug、架构和 review 里价值很高，但这类输出天然包含推断。现在规则没有要求区分：

- 已从代码/日志证实
- 高概率推断
- 待验证猜测

建议让 review/分析产物固定带三个区块：

- `Confirmed`
- `Inferred`
- `Needs Verification`

这样 Cursor 在汇报用户时不会把推断包装成事实。

### 11. 缺少“回滚和恢复”规范

README 已经提到 session 续接待完善，但缺的不只是 resume，还有失败后的恢复策略：

- 子任务写坏后怎么回退
- 哪些产物可删，哪些必须保留
- 同一任务重跑时是否覆盖旧文件
- review 和执行稿如何区分版本

建议：

- `_agent_work/` 内输出按时间戳或任务 ID 命名
- 计划、执行日志、review 分开存
- 对写操作任务记录“目标文件列表”和“验证结果”

### 12. 缺少用量策略和路由策略的联动规则

现在用量查看是单独一个 Skill，但没有真正接入调度决策。

更完整的策略应该是：

- Cursor fast quota 低于阈值时，默认禁止大上下文读取
- Codex 周额度低于阈值时，只保留给 review/根因分析
- cc 余量紧张时，减少并行实例数

否则“查看用量”和“实际调度”是两套分离系统。

## 四、建议的升级方向

### 13. 从“说明文档”升级为“可执行 runbook”

现在的文档可读性不错，但更像知识说明，而不是严谨操作手册。

建议在 `dispatch-ai-agents` Skill 中加一个强制 runbook：

1. 判断任务等级和风险
2. 判断主执行者
3. 判断是否需要前置探路
4. 生成 handoff 文件
5. 执行
6. 跑验证
7. 生成 review/总结
8. 再决定是否交下一个工具

这样 Agent 不是“记住原则”，而是“照流程走”。

### 14. 定义推荐组合，而不是只定义单工具职责

你现在已经有一个经典组合示例，但还可以再前进一步，明确推荐编排模式：

- 模式 A：Cursor 决策 -> cc 批量执行 -> Cursor 验收
- 模式 B：cc 探路 -> Codex 定方案 -> cc 落地 -> Codex review
- 模式 C：Cursor 小改 -> Codex review
- 模式 D：高风险任务 -> Codex 出方案和检查点 -> Cursor/cc 按检查点执行

真正稳定的多工具体系，关键不是“谁厉害就派给谁”，而是“哪类问题走哪条流水线”。

### 15. 为 Codex 明确限定职责，避免被当成昂贵执行器

从当前描述看，你已经意识到 codex 稀缺，但规则还可以更硬一点：

- Codex 默认不做海量文件通读
- Codex 默认不承担机械批量改动
- Codex 优先用于：
  - 根因分析
  - 方案对比
  - patch 风险审查
  - 边界条件和回归点识别

也就是让 Codex 更像“审稿人/架构师/疑难问题医生”，而不是“第二个执行工人”。

### 16. 让 review 输出结构化，便于 Cursor 最终对用户汇报

Codex 的 review 若想真正发挥价值，建议固定输出为：

- `Findings`
- `Severity`
- `Why it matters`
- `Suggested fix`
- `Verification status`

这样 Cursor 很容易把它转成最终用户可读结论，也便于后续多次 review 对比。

## 五、具体落地建议清单

如果只做最小改动，我建议优先做这 8 件事：

1. 统一所有示例输出路径到 `_agent_work/`，删除 `/tmp/` 旧示例。
2. 把调度标准从“任务类型”升级成“推理强度 + 执行规模 + 风险 + 可验证性”四维矩阵。
3. 给 cc/codex 交接产物定义固定模板，而不是只靠自然语言。
4. 把 `--dangerously-skip-permissions` 从默认命令里降级为特例命令。
5. 为 codex 增加 CLI 健康检查，不要只做 TUN 检测。
6. 增加并行写入协议，禁止多实例无 ownership 地同时改同一片文件。
7. 把验证闭环写进 Skill，明确不同任务最低验证要求。
8. 把 `check-ai-usage` 的结果真正接入调度阈值，而不是只做展示。

## 六、一句话总结

这套体系的核心分工是合理的，但目前还偏“经验驱动的调度建议”。如果想让它在复杂任务里稳定工作，下一步不是继续补更多口号，而是把它补成一套有统一产物、有风险分级、有验证闭环、有交接模板的执行协议。
