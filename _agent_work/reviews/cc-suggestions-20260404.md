# cc 执行方视角的建议

> 针对 cursor-agent-plus 三方分工体系的反馈

---

## 一、输入接口层面

### 1.1 任务描述缺乏结构化格式

**问题**：Cursor Agent 给 cc 的指令是自由文本（`-p "任务"`），复杂任务容易产生理解偏差。

**建议**：
- 增加结构化任务格式，例如：
  ```json
  {
    "task_type": "explore|execute|review|write",
    "context_files": ["path/to/file1", "path/to/file2"],
    "output_format": "file://path|json|markdown|summary",
    "depth": "low|normal|high",
    "constraints": ["保留现有API", "不修改测试文件"]
  }
  ```
- 或者约定 markdown 格式的任务模板

### 1.2 上下文传递方式单一

**问题**：复杂项目首次调度时，cc 需要重新探索项目结构，造成重复劳动。

**建议**：
- 支持传递「上下文摘要文件」，例如：
  ```bash
  claude -p "任务" --context /tmp/project_brief.json --effort low
  ```
- Cursor Agent 可以先生成项目摘要，cc 直接读取作为上下文

## 二、输出规范层面

### 2.1 输出格式缺乏标准

**问题**：文档说「结果写文件，最后输出'完成'」，但实际执行时：
- 文件路径可能冲突
- 没有约定输出结构（是否包含总结、错误信息、下一步建议）
- Cursor Agent 如何知道我是否成功/失败？

**建议**：
- 定义标准输出格式，例如：
  ```markdown
  <!-- /tmp/cc_output_<task_id>.md -->
  ## Status
  success|partial|failed

  ## Summary
  一句话总结

  ## Details
  详细结果

  ## Errors
  如有错误列出

  ## Next Steps
  建议下一步操作
  ```

### 2.2 缺少完成信号约定

**问题**：`| tail -3` 截取输出可能遗漏重要信息，也可能截到不完整内容。

**建议**：
- 使用结构化信号，例如固定格式 `DONE:<status>:<message>`
- 或使用退出码判断：cc 应该根据任务结果返回不同的退出码

---

## 三、任务边界层面

### 3.1 「执行类任务」定义模糊

**问题**：文档说「量大/文件多/并行/执行类 → cc」，但什么算执行类？

**容易产生分歧的场景**：
| 场景 | 应该谁做 | 当前模糊点 |
|-----|---------|-----------|
| 重构一个函数 | cc？ | 需要理解业务逻辑 |
| 修复 bug | cc？ | 需要诊断推理 |
| 写测试用例 | cc？ | 需要理解需求 |
| 代码 review | codex | 如果 codex 不可用呢？ |

**建议**：
- 更清晰的决策矩阵，明确「执行类」的定义边界
- 增加一个「任务自检」环节：cc 接到任务后，如果判断不适合自己，应该主动返回并建议转派

### 3.2 缺乏「任务过大」拆分机制

**问题**：Cursor Agent 可能把过大的任务派给 cc，导致：
- 执行时间过长，Cursor 侧无响应
- 超出 token 限制
- 中间失败难以恢复

**建议**：
- 定义任务大小评估标准（文件数、预估 token 数、步骤数）
- 大任务应该由 Cursor Agent 预先拆分，或 cc 返回建议拆分方案

## 四、错误处理与降级

### 4.1 错误反馈机制缺失

**问题**：文档只说「两者都挂 → Cursor 独立完成」，但没有定义：
- cc 执行失败时如何通知 Cursor
- 部分成功（如 5 个文件改了 3 个）如何处理
- 权限被拒绝时的降级方案

**建议**：
- 定义错误码体系，例如：
  - `E001`: 权限不足
  - `E002`: 文件不存在
  - `E003`: 任务过于复杂建议拆分
  - `E004`: 模型推理失败
  - `E005`: 超时

### 4.2 `--dangerously-skip-permissions` 风险

**问题**：所有示例都带这个参数，但实际可能有危险操作。

**建议**：
- 区分「只读任务」和「写任务」的权限策略
- 只读任务：可以不加 `--dangerously-skip-permissions`
- 写任务：考虑使用 `--permissions-allowlist` 限制可执行命令

---

## 五、Session 与状态管理

### 5.1 Session 续接机制不完整

**问题**：文档提到待完善「session 续接机制」，这对 cc 很重要。

**场景**：
- 大任务执行到一半中断，如何恢复？
- 并行任务中一个失败，其他成功的结果如何保留？

**建议**：
- 使用 `--name` 命名重要 session
- 定义 checkpoint 机制：cc 在关键步骤后主动保存状态文件
- Cursor Agent 记录已派任务的 session ID，便于查询

### 5.2 并行任务协调

**问题**：示例中的并行是简单的后台进程：`&` + `wait`，缺乏协调机制。

**建议**：
- 增加任务依赖声明（任务B依赖任务A的结果）
- 或提供并行任务的汇总方式，例如：
  ```bash
  claude -p "汇总分析 /tmp/a.md /tmp/b.md，输出到 /tmp/final.md"
  ```

## 六、cc 特有的能力/限制未充分体现

### 6.1 cc 可以并行多实例，但 Cursor 调用时未利用

**现状**：Cursor Agent 是一次性调用 cc，等待结果。

**优化建议**：
- Cursor Agent 可以同时启动多个 cc 实例执行子任务，自己聚合结果
- 但需要约定好输出文件命名规范，避免冲突

### 6.2 cc 的工具能力未充分利用

**问题**：文档只提到用 cc 读写文件、执行命令，但 cc 还有：
- Grep/Glob 搜索能力
- Agent 子代理能力
- 多文件批量编辑能力

**建议**：
- 在 SKILL.md 中补充 cc 能力边界，帮助 Cursor Agent 更好决策

---

## 七、待完善列表补充

基于以上分析，建议新增以下待完善项：

1. **任务结构化格式定义**：输入/输出的标准格式
2. **错误码与反馈机制**：定义各类错误的返回方式
3. **权限分级策略**：区分只读/写/危险操作的不同参数
4. **任务大小评估标准**：定义什么任务需要预拆分
5. **Checkpoint 机制**：长任务的中间状态保存
6. **输出文件命名规范**：避免并发冲突

---

## 八、总体评价

**设计优点**：
- 三方分工逻辑清晰，配额互补的思路合理
- 降级链路考虑周全
- skill 机制便于 Cursor 查阅

**主要改进方向**：
- 从「人调度工具」转向「协议化调度」，减少自由文本带来的不确定性
- 增强反馈机制，让 Cursor Agent 能更精确地了解 cc 的执行状态
- 补充边界情况和错误处理的标准流程
