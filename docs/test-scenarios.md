# 分工测试任务集

> 每次迭代规则/skill 后，从中挑 2-3 个跑一遍，统计实际分工占比，与期望对比。

---

## 使用方法

1. 开一个**新对话**（确保规则从零加载）
2. 用 `/army` 触发，把下面的任务描述贴进去
3. **只看计划阶段**的分工表——不需要真的执行完（省配额）
4. 记录：Cursor 分了几步给自己、cc 几步、codex 几步
5. 对照下方「期望分工」，看是否达标
6. 如果想完整测试，确认后让它执行，结束后统计实际 tool call 占比

---

## 评分标准

| 指标 | 达标 | 不达标 |
|---|---|---|
| Cursor 自己做的步骤占比 | ≤ 40% | > 40% |
| 该派 cc 的有没有派 | 全部派出 | 有遗漏 |
| 该派 codex 的有没有派 | 全部派出 | 有遗漏 |
| 可并行的有没有标记并行 | 标记了 | 串行执行 |
| 产物是否要求写文件 | 全部写文件 | 有 stdout 回传 |

**健康度 = 达标项 / 5**。目标：≥ 4/5。

## 测试任务

### T1：批量文档统一格式

**任务描述**（贴给 /army）：
```
把 skills/dispatch-ai-agents/ 下的 4 个 md 文件（SKILL.md、cc-reference.md、
codex-reference.md、collaboration.md）统一格式：每个文件开头加上
「最后更新：YYYY-MM-DD」，所有一级标题改为带编号（1. xxx、2. xxx），
检查是否有断链或引用不一致的地方。
```

**期望分工**：

| 步骤 | 谁做 | 理由 |
|---|---|---|
| 批量格式修改（4 个文件） | cc | ≥3 文件同类操作 → 铁律触发 |
| 检查引用一致性 | cc 或 codex | 需要交叉比对 |
| 验收改动 | Cursor | 调度者职责 |

**关键检查点**：
- [ ] Cursor 没有自己逐个文件改格式
- [ ] cc 被派去做批量编辑
- [ ] 4 个文件的改动要求并行或一次性派给 cc

---

### T2：多文件 Review

**任务描述**（贴给 /army）：
```
Review 这三个文档的质量：docs/concept.md、docs/roadmap.md、docs/not-adopted.md。
每个文档从「内容准确性、结构清晰度、与实际代码的一致性」三个维度评分，
给出具体改进建议。
```

**期望分工**：

| 步骤 | 谁做 | 理由 |
|---|---|---|
| review 3 个文档 | cc 并行（3 实例）或 cc + codex 混合并行 | ≥2 文件 review → 派 cc；可并行 |
| 汇总 review 结果 | Cursor | 调度者职责 |

**关键检查点**：
- [ ] 没有 Cursor 自己读完 3 个文件然后自己写 review
- [ ] review 任务派给了 cc/codex
- [ ] 3 个文件的 review 标记为并行执行
- [ ] 每个 review 结果要求写到 `_agent_work/reviews/`

---

### T3：多模块上下文搜集

**任务描述**（贴给 /army）：
```
我要重构这个项目的文档体系。先搜集以下 3 个模块的上下文：
1. rules/ 目录：当前规则内容、与 skill 的关系
2. skills/ 目录：所有 skill 的结构、子文档引用关系
3. docs/ 目录：文档之间的交叉引用、与实际配置的一致性
每个模块输出一份结构化摘要。
```

**期望分工**：

| 步骤 | 谁做 | 理由 |
|---|---|---|
| 搜集 3 个模块上下文 | cc 并行（3 实例） | ≥3 模块独立搜集 → 派 cc 并行 |
| 综合分析、出重构方案 | codex 或 Cursor | 需要深度推理 |
| 向用户汇报 | Cursor | 调度者职责 |

**关键检查点**：
- [ ] 3 个模块的上下文搜集并行执行
- [ ] 搜集任务派给 cc，不是 Cursor 自己读
- [ ] 每个摘要写到 `_agent_work/context/`
- [ ] 综合分析如果复杂，派 codex

---

### T4：深度架构 Review + 落地

**任务描述**（贴给 /army）：
```
审查当前的降级策略是否完善：
1. 读 SKILL.md 的降级策略段、cc-reference 和 codex-reference 的相关内容
2. 分析是否覆盖了所有失败场景（网络断、配额耗尽、输出异常、工具版本变化）
3. 如果有遗漏，给出补全方案并落地修改
```

**期望分工**：

| 步骤 | 谁做 | 理由 |
|---|---|---|
| 搜集降级相关上下文 | cc | 需要读多个文件 |
| 深度分析是否完善 | codex | 架构决策 → 派 codex |
| 落地修改 | cc | 按 codex 方案批量改文件 |
| 验收 | Cursor 或 codex | 调度者验收或 codex review |

**关键检查点**：
- [ ] 使用了模式 B 或 D（cc 探路 → codex 定方案 → cc 落地）
- [ ] codex 做了深度分析，不是 Cursor 自己分析
- [ ] 落地改动派给 cc，不是 Cursor 逐个文件改

---

### T5：简单小改（对照组）

**任务描述**（贴给 /army）：
```
把 README.md 里的「agent-army」标题改成「Agent Army」，首字母大写。
```

**期望分工**：

| 步骤 | 谁做 | 理由 |
|---|---|---|
| 改一行标题 | Cursor 自己做 | ≤2 文件、≤50 行 → 不需要外派 |

**关键检查点**：
- [ ] Cursor 直接自己做了，没有过度拆解
- [ ] 没有无谓地启动 cc/codex

## 迭代流程

```
改规则/skill → 跑 2-3 个测试任务 → 记录分工 → 对比期望 → 发现问题 → 改规则/skill → ...
```

建议每次迭代至少跑 T1 或 T2（最容易暴露"Cursor 自己做"的问题）+ T5（确认没有过度拆解）。
